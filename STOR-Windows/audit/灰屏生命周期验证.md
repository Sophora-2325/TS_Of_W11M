# 截图生命周期验证

本轮改的是截图会话的时序和竞争，不是翻译、查词或密钥。纯色灰屏在修复前可以被稳定做成“第一次有内容、后面变成纯色”；修复后的同一探测和正式窗口验收没有再出现这种纯色底图。历史上没有留下现场的那次偶发纯灰，不能据此宣称所有纯灰都已消失。

## 复现到的失败

修复前，框选层一旦显示过，下一次 GDI `BitBlt` 会出问题：

- 只异步隐藏窗口时，底图会一轮比一轮暗，因为截进了仍在合成里的遮罩。三次窗口平均亮度约 71.5、51.6、37.7。
- 等主线程真正隐藏并做显示亲和性排除后，第二次和第三次捕获变成纯色：`rgb_spread=0`，`alpha_zero_pct=0`，窗口平均亮度约 0.1。第一次仍是 `rgb_spread=255`。

这不是用“接近纯色就判失败”推断的。对照是同一进程里紧挨着的第一次捕获，以及 JPEG 体积从约 30 万字节掉到固定的 112627 字节。

## 最终做法

顺序是：创建会话并固定显示器 → 在主线程销毁旧框选层并等待完成 → 隐藏原浮窗 → 连续两次 `DwmFlush` → 用 `GetDC(NULL)` 捕获这块显示器 → 编码并按 sessionId 保存 → 重建框选层 → 前端加载成功 → 再显示。

`DwmFlush` 失败会取消这一轮，不用固定睡眠代替。纯色只写入诊断字段，不单独当成失败条件。

## 失败恢复

`audit/evidence/gray-lifecycle-failure.json` 记录的是销毁框选层之前的构建：前端 `Image.decode` 被拒绝后，`reopen_overlay` 返回“底图解码失败”，浮窗重新显示，原文仍是“生命周期验收原文”，错误区显示同一句，阶段里没有 `shown`，有 `restore-popup`。

最终 exe 又试了一次。新框选页是捕获后才创建的，注入赶在解码前的尝试失败，这一轮实际走到了 `image-ok` 和 `shown`，浮窗被正常关掉。所以最终二进制没有再次打中“解码失败后恢复浮窗”的窗口路径。状态机测试 `image_failure_is_not_ready_and_live_mode_does_not_wait_for_an_image` 仍然通过。

## 剩余限制

- 没有把这次修掉的“重复截图变成纯色”说成历史上每一次偶发纯灰的全部原因。若再出现，看 `get_capture_trace`：`encoded` 的 `rgb_spread=0` 偏向捕获缓冲；扩散高但窗口仍是灰的，偏向窗口渲染。
- 关闭冻结画面的实时截图仍走原来的 xcap 捕获。它也会先销毁框选层，但这次窗口验收没有关掉冻结设置，所以这条路径没有实窗数据。
- 远程桌面如果 `DwmFlush` 失败，这一轮会直接失败并恢复浮窗或设置页，不会用睡眠硬截。
- 最终 exe 上的解码失败恢复没有再次用窗口打中，见上文。
